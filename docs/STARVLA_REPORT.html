1. Overview

StarVLA is a research codebase that treats Vision-Language-Action (VLA) models the way PyTorch treats neural networks: as a collection of swappable building blocks rather than a monolithic stack. A VLA extends a Vision-Language Model (VLM) so it can not only "see" and "speak" but also "act" — that is, take an image plus a natural-language instruction and emit a continuous robot action sequence.

Per the project's own framing, StarVLA introduces "a backbone-action-head decomposition, where a shared vision-language backbone encodes the scene and instruction, and a pluggable action head maps the resulting representation to motor commands." The same backbone can drive different action heads; the same head can be mounted on different backbones. This is the "Lego" part.

Output shape Actions are emitted as a tensor of shape [batch, action_horizon, action_dim] — typically a chunk of 8–16 future joint-space targets per inference call, which an outer loop executes open-loop before re-querying the policy.

2. Framework Architecture

StarVLA is structured around four replaceable layers:

Figure 1 — StarVLA's four-layer decomposition. The backbone and action head are independently swappable; the dataloader provides a unified sample schema across robots.

2.1 Backbone

The backbone is a fully pretrained vision-language model (or, optionally, a world model). In the codebase's reference recipe for OpenArm O6 it is Qwen/Qwen3-VL-4B-Instruct — a 4-billion-parameter VLM trained on broad web-scale image + text + video data. The backbone produces a sequence of multimodal hidden states that the action head cross-attends to.

2.2 Action Head

Four heads ship in-tree, each implementing a different action-modeling philosophy. Heads vary from a few-MLP-layers continuous regressor (OFT) to a 16-layer flow-matching transformer (GR00T). They all consume the backbone's hidden states and a current proprioception vector ("state"), and produce normalized action chunks.

2.3 Dataloader

StarVLA uses the LeRobot data format and supports mixture training across multiple embodiments. Normalization is configured per-modality (q99, min_max, mean_std, or binary). The dataloader applies transforms (resize, normalize) inside a ComposedModalityTransform and returns samples in a common {image, lang, state, action} schema after a final _pack_sample step.

2.4 Framework "Glue"

A Framework class (e.g. QwenGR00T, QwenOFT, QwenPI) wires a specific backbone to a specific action head and implements forward() and predict_action(). Per the project FAQ, "data preprocessing takes <1% time in profiling; keeping it inside the Framework allows model-specific handling without leaking assumptions into the dataloader."

3. Four Shipping Paradigms

StarVLA-FAST

discreteautoregressive

Treats the action stream as discrete tokens emitted from the LLM vocabulary. Fastest training (just next-token loss), no separate head. Trade-off: discretization noise on fine motor commands.

StarVLA-OFT

continuousregression

Lightweight MLP-style head on top of the VLM's hidden states, trained with L1 regression. Simple, very fast inference, surprisingly strong benchmark results (LIBERO 96.6%). Trade-off: deterministic output, no multi-modal distribution over actions.

StarVLA-π

flow-matchinglayerwise

A layer-wise cross-DiT "expert" trained with flow matching. The action head sees the VLM features at multiple depths via cross-attention. More parameters, more expressive distribution. Trade-off: more compute at inference.

StarVLA-GR00T

flow-matchingdual-system

Dual-system "System 1 / System 2" inspired by the GR00T family. The VLM acts as the slower "thinker" and a flow-matching DiT acts as the faster "doer". This is the paradigm used for the OpenArm O6 work in this repository.

Important: published paradigms ≠ pretrained weights The names FAST / OFT / π / GR00T come from published external papers (Physical Intelligence's π₀, NVIDIA's GR00T, etc.). StarVLA reimplements those architectures inside its framework but does not ship pretrained weights from the original publications. See Section 5 and Q5 of this report for the full implication.

4. QwenGR00T vs Isaac-GR00T N1.5 — Configuration

The two systems are architectural cousins — both pair a pretrained VLM with a flow-matching DiT action head. The table below highlights where they agree and where they diverge.

QwenGR00T — pros & cons

Pros

  • Larger, newer VLM (Qwen3-VL ≈ 4 B) with stronger general vision & language understanding (better MMMU, DocVQA).
  • Higher VLM hidden dim → richer cross-attention conditioning for the action head.
  • Permissive MIT license; fully open weights.
  • Direct action / state dims — no padding overhead.

Cons

  • Action head is cold — every fine-tune teaches it "how to denoise actions" from scratch.
  • ~2× VLM compute per forward vs Eagle 2.
  • Sampler is plain 4-step Euler; DDIM kwargs are wired in but silently dropped (dead code).
  • No built-in image augmentation; relies entirely on data diversity.

Isaac-GR00T N1.5 — pros & cons

Pros

  • Action head pretrained on millions of cross-embodiment robot trajectories — strong prior, fast convergence on small data.
  • Compact VLM (≈ 2 B) → faster inference per step.
  • Built-in color jitter + crop augmentation improves robustness.
  • Universal action padding eases multi-robot transfer.

Cons

  • Older / smaller VLM — weaker general vision & language understanding than Qwen3-VL.
  • NVIDIA license — usage and redistribution constraints.
  • Padding to 32 / 64 dims wastes capacity for low-DOF robots.
  • Less framework flexibility — single architecture, not a "swap-anything" codebase.

5. Pretraining State (cold vs warm)

This is one of the most important practical points and is often misunderstood. StarVLA's individual components arrive at fine-tuning time with very different amounts of prior knowledge — visualized below as the share of each component that comes "warm" (already trained on robot data), "web-pretrained" (trained on internet-scale text+image data), or "cold" (random init).

Figure 2 — In QwenGR00T, the action head and adapter are cold at fine-tune time; only the VLM brings prior knowledge (and it knows nothing about robot dynamics). In N1.5, both the VLM and the action head carry robotics-relevant priors into the fine-tune.
Why this is the dominant factor in the MSE gap Fine-tuning StarVLA on a small dataset (say 1000 episodes) has to teach the action head how to be an action head from scratch, in addition to learning the specific task. N1.5's head only needs to specialize an already-strong robotics prior. On large benchmark datasets (LIBERO, RoboCasa), StarVLA's cold head can still hit competitive numbers because the data is large enough to learn from scratch — but on small fine-tunes the gap is visible.

6. Training Pipeline

6.1 Loss

The flow-matching action head is trained to predict the velocity field that transports random noise into the target action trajectory. Per-batch, each ground-truth chunk is repeated repeated_diffusion_steps (default 8) times with different noise samples and timesteps; the MSE between the predicted and ground-truth velocity is the loss. There is no separate VLM loss (loss_scale.vlm: 0.0) in robot-only training, though the codebase supports interleaved VLM co-training.

6.2 Optimization

  • Mixed precision: bfloat16 autocast around the VLM forward, float32 around the DiT step.
  • Optimizer: AdamW with per-group learning rates — base, qwen_vl_interface, action_model can each be set independently.
  • Scheduler: cosine with a minimum learning rate floor.
  • Distributed: Hugging Face Accelerate; DeepSpeed ZeRO-2 supported for multi-node.
  • Resume: uses Accelerator's checkpoint mechanism to fully save and restore optimizer state, LR scheduler, and other training state.

6.3 Freezing

Backbones are frozen via a comma-separated list under trainer.freeze_modules. The single-GPU recipe in the FAQ recommends keeping the VLM frozen and training only the action head, especially on 24 GB cards. This is a practical compromise, not always the optimal choice — unfreezing the VLM is the highest-impact single change for small-data fine-tunes (see Section 10 Path A).

7. Advantages

  • Modularity by design. Swapping the backbone or the action head is a config change, not a refactor.
  • Modern VLM. Qwen3-VL is a current-generation VLM with native dynamic-resolution ViT, long-context language decoder, and strong benchmark results on MMMU / MathVista / DocVQA.
  • Multiple action-head paradigms in one codebase. FAST, OFT, π, and GR00T heads all share the same data loaders, evaluator, and training loop — apples-to-apples comparison is straightforward.
  • Cross-embodiment ready. The LeRobot mixture interface allows multi-robot training out of the box, with per-modality normalization stats and embodiment tags.
  • Strong benchmark numbers. Reported results include LIBERO 96.6%, SimplerEnv WidowX 65%, RoboTwin 2.0 ~88% across heads.
  • Unified sim/real deployment. Inference exposes a websocket-served policy that uses the same observation/action dictionary format in simulation and on real hardware.
  • Reproducible recipes. Each benchmark ships with a minimal "single-benchmark" YAML so results can be regenerated without digging through framework internals.

8. Shortcomings & Limitations

The single biggest limitation StarVLA ships with no pretrained action-head weights. Every fine-tune starts from a randomly initialized head — a serious disadvantage on tasks where the dataset is too small to teach the head "how to denoise actions" from scratch.
  • Cold action head. See callout above and section 5.
  • Default sampler is bare-bones. Flow-matching uses fixed-step Euler integration. Training code references DDIM kwargs (use_ddim=True, num_ddim_steps=20) that are silently dropped. Raising the step count to 16–20 substantially cleans up open-loop output.
  • VLM frozen by default in the single-GPU recipe. The 4 B Qwen backbone never adapts to the target visual domain. Unfreezing doubles VRAM but is the highest-impact single change.
  • Cross-embodiment uses unified padding. Different robots reconciled by zero-padding to a common universal dim. Embodiment-specific structure is not preserved end-to-end.
  • RL fine-tuning is "ongoing". Released paradigms are behavior-cloning; online RL or DPO-style preference fine-tuning are not yet first-class.
  • Multi-node scaling plateaus. Around ~79% efficiency beyond 32 GPUs, primarily due to VLM forward dominating step time.
  • Single-GPU is slow. On 1× RTX 4090 + Qwen2.5-VL-3B, a typical benchmark "may take several days."
  • Confusing default training metric. Historic mse_score = np.linalg.norm(diff) / num_pots is monotonic with quality but not interpretable. (This repo now logs classical MSE.)

10. Recommendations for Improvement

Three paths, ranked by effort. For most users the recommended sequence is Path A → re-evaluate → only proceed to B or C if the residual gap matters for the downstream task.

10.1 Path A — Unfreeze the VLM and train longer (1–2 days)

The lowest-effort improvement. Edit starvla_train_openarm_o6.yaml: 

trainer:
  max_train_steps: 200000          # was 100000
  freeze_modules: ""                # was "qwen_vl_interface"
  learning_rate:
    base: 5.0e-06                  # was 1.0e-05
    qwen_vl_interface: 5.0e-06     # was 1.0e-05
    action_model: 5.0e-05          # keep

Lets Qwen3-VL adapt to the can-sorting visual domain. With the VLM unfrozen, per-step VRAM roughly doubles; drop per_device_batch_size from 16 to 4 and raise gradient_accumulation_steps to 8 to preserve the effective batch size. Expected MSE improvement: 30–50%.

10.2 Path B — Pretrain on a larger mixture, then fine-tune (3–7 days)

Train StarVLA on a much larger dataset (DROID, OpenX subset, LIBERO) for ~300–500 k steps, then fine-tune on can-sorting for another 50 k. This reproduces the recipe NVIDIA used to make the N1.5 head warm. Expected MSE improvement: 5–10×. Cost: substantial GPU time + curating a multi-robot mixture.

10.3 Path C — Direct action-head warm-start (1–3 days experimentation)

Load the action head from nvidia/GR00T-N1.5-3B and copy the dim-compatible tensors (self-attention Q/K/V/O, FFN, AdaLN modulation) while freshly initializing layers that depend on action_dim / state_dim / cross-attention dim (those differ between StarVLA and N1.5). Risk: partial transfer can be worse than cold init if internal layer interactions diverge.

10.4 Deployment-time quick wins (no retraining)

  • Raise inference steps from 4 to 16–20. Drops MSE by ~3× and visibly smooths the per-DOF trajectory plots. Single config change.
  • Keep the low-pass filter on the action stream. Lowering alpha from 0.3 → 0.15–0.20 smooths further at the cost of a small lag.
  • Verify state normalization at the deployment edge. The StarVLA server expects q99-normalized state input; raw joint angles cause "jitter at init"-style failures.
